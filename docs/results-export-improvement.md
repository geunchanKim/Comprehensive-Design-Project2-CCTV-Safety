# CSV 결과 조회의 메모리 사용 개선과 자소서 활용

작성일: 2026-11-19. 기준 코드: 원격 확인 후 `origin/develop`의 `c51d7a2`.
작업 브랜치: `perf/bounded-results-export`. 기존 작업 폴더의 미커밋 변경과 별도 PPE·쿼리 개선 worktree를 보존하고 `.csv-export`에서 작업했다.

## 실제로 확인한 문제

`GET /sessions/{session_id}/results.csv`는 탐지와 위험 기록을 각각 `.all()`로 가져오고, ORM 객체와 JSON 열을 모두 로드했다. 카메라 중복 제거를 위한 집합도 전체 세션 크기만큼 커졌다. 이후 전체 CSV를 `StringIO`에 작성하고 문자열·응답 바이트로 변환했다. 즉 파일을 내보내기 위해 원본 객체, 중복 제거 정보, 파일 전체를 서버 메모리에 동시에 보유했다.

이 API는 위치·위험 결과를 검증하고 보관하는 실제 기능이다. 11/18 v94 연동 기록에서도 CSV 다운로드를 사용했다. 다만 그날의 관측만으로 메모리 부족이나 서버 장애가 발생했다고 말할 수는 없다. 이번에는 기록이 누적되는 조건을 별도 재현해 자원 사용이 증가하는 구조를 확인하고 개선했다.

열린 작업 기록의 입력 종료 후 남은 PPE 경고도 중요한 후속 과제다. 하지만 경고 종료·확인 상태·일시 누락 연결은 팀 정책과 화면 계약이 필요한 항목이다. 이번 변경에서는 그 정책이나 운영 위험 분석 설정을 변경하지 않았다.

## 구현

- 필요한 CSV 열만 조회하고, DB의 `row_number()`로 `(bundle_id, object_id)` 중복을 제거한다. 기존의 가장 이른 관측과 정렬 순서를 유지한다.
- 조회 결과를 500행 단위로 가져와 ORM 객체·JSON 전체 적재를 없앤다.
- CSV는 1MiB까지 메모리 버퍼에 작성하고 초과하면 임시 디스크 파일로 전환한다.
- 파일 준비를 끝낸 후 64Ki 문자 청크로 전송한다. 느린 다운로드가 DB 커서를 붙잡지 않게 한다.
- 정상 종료, 쿼리 실패, 전송 중단에 대비해 임시 파일을 닫는다. 파일명은 UTF-8 다운로드 헤더로 인코딩한다.

단순히 `.all()`만 없애면 CSV 전체 문자열과 중복 제거 집합이 계속 커진다. 세 부분을 함께 바꾼 것이 이번 개선의 핵심이다. 위치·위험 CSV 열이나 탐지 알고리즘, API 조건별 격리 규칙은 변경하지 않았다.

## 측정 방법과 결과

별도 로컬 임시 SQLite DB에 두 카메라 탐지 2행과 위험 1행을 프레임 묶음마다 넣었다. 출력은 중복 제거된 위치 1행과 위험 1행이다. 기준 커밋에서 기존 내보내기 함수를 추출해 같은 DB와 설정으로 실행했다. 두 경로를 예열한 뒤 실행 순서를 교대로 바꿔 각각 3회 측정했다. 출력은 메모리에 누적하지 않고 SHA-256으로 비교했다.

수치는 `output/benchmarks/results-export.json`의 원본 실행 결과와 아래 표를 함께 본다. 메모리는 `tracemalloc`의 최대 Python 할당량이며 프로세스 RSS, DB 서버 메모리, OS 파일 캐시를 포함하지 않는다. 시간은 메모리 추적을 켠 함수 실행·파일 소비 시간으로 HTTP·네트워크·화면 지연이나 운영 처리량이 아니다.

| CSV rows | Before peak Python MiB | After peak Python MiB | Reduction | Before seconds | After seconds |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 20,000 | 59.55 | 1.82 | 96.95% | 3.76 | 1.71 |
| 100,000 | 295.47 | 1.76 | 99.41% | 27.98 | 10.37 |

전체 실행에서 CSV 길이와 SHA-256이 전후 동일했다. 추가 회귀 테스트에서는 카메라별 시각이 다를 때의 대표 관측, 배치 경계, 프로필 격리, 미매칭 탐지 제외, 빈 결과, CSV 인용 문자, 임시 파일 전환·정리도 확인했다.

시간은 10만 행 개선 후 9.09 / 35.41 / 10.37초로 변동했다. 중앙값은 감소했지만 개선 후 최대 시간이 기존 최대 시간보다 길어, 일정한 응답 속도 향상이나 운영 지연 개선으로 일반화하지 않는다. 자소서 성과의 중심은 메모리 감소와 결과 보존이다.

검증: 백엔드 135개, 엣지 61개 통과. 처음 pytest 실행은 상위 경로 `C:\conftest.py`의 외부 의존성 `trustme` 부재 때문에 수집이 실패했다. 저장소를 rootdir/confcutdir로 지정해 프로젝트 테스트를 실행했다.

```powershell
python -m pytest --rootdir=. --confcutdir=. backend/tests -q
python -m pytest --rootdir=. --confcutdir=. ai/tests -q
python tools/benchmarks/results_export.py --pairs 10000 50000 --repeats 3
```

## 해석과 남은 한계

메모리 사용을 임시 디스크와 DB 정렬 작업으로 옮기는 절충이다. 임시 디스크 용량이 필요하고, 동시 다운로드 수만큼 파일과 작업 부하가 추가된다. 이번 작업은 동시 요청 제한이나 다운로드 인증을 도입하지 않는다. CSV 작성 전 완료를 기다리는 방식이므로 최초 응답 지연 개선을 주장하지 않는다.

SQLite 합성 데이터 결과이며 실제 PostgreSQL의 실행 계획·정렬 메모리·디스크와 다중 사용자 부하 검증은 별도다. 실시간 탐지 처리 지연 개선, 메모리 부족 장애 해소, 운영 비용 절감, 정확도 향상은 이번 결과로 증명하지 않았다. 작성 중 새 입력이나 재계산이 동시에 실행되는 경우의 일관된 시점 보장도 새로 추가하지 않았다.

## 자소서에서 사용할 이야기

금융권에는 대량 거래·정산·내역 다운로드와 같은 업무에서의 자원 관리 역량으로, 공기업에는 장기 누적 기록의 안정적 조회와 검증 가능한 증빙 관리 역량으로 연결해 설명할 수 있다. 실제 프로젝트는 산업현장 CCTV 관제이며 금융 서비스를 개발한 경험으로 바꾸어 쓰지 않는다.

문제 발견은 “CSV 결과 보관 기능을 점검하다 전체 기록을 한꺼번에 메모리에 적재하는 구조를 확인했다”, 행동은 “중복 제거·조회·파일 생성 세 구간을 함께 개선하고 동일 조건으로 비교했다”, 성과는 아래 측정 수치로 말하면 된다. 팀의 실측 정확도나 엣지 전송 지연 수치를 이번 개인 개선 성과로 섞지 않는다.

산업현장 안전관제 시스템의 백엔드를 개발하면서, 누적 결과를 CSV로 내려받는 기능이 전체 데이터를 한꺼번에 메모리에 적재한다는 문제를 발견했습니다. 기록이 쌓일수록 서버 자원 부담이 커질 수 있어, 필요한 열만 배치로 조회하고 중복 제거를 DB에서 수행하도록 개선했습니다. 파일 생성도 일정 크기를 넘으면 임시 디스크를 사용하도록 바꿨습니다. 개선 효과는 같은 합성 데이터로 각 3회 비교했습니다. CSV 10만 행 조건에서 최대 Python 메모리 할당량의 중앙값을 295.47MiB에서 1.76MiB로 약 99.4% 줄였고, 전후 파일의 해시 일치와 백엔드·엣지 테스트 196개 통과로 결과 보존과 기존 기능을 검증했습니다. 이 경험으로 누적 데이터의 자원 사용을 재현하고, 정확한 결과를 유지하면서 개선 효과를 수치로 확인하는 방법을 배웠습니다.

면접에서 “실제로 서버가 다운됐나요?”라고 물으면 “다운 장애가 발생했다고 주장하는 사례는 아닙니다. 누적 데이터로 자원 사용 증가를 재현하고 선제적으로 개선했습니다”라고 답한다. “메모리 전체가 99% 줄었나요?”에는 “특정 CSV 내보내기 경로의 최대 Python 할당량을 같은 합성 데이터로 비교한 수치입니다”라고 범위를 분명히 한다.

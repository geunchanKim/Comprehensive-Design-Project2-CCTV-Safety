# 재계산 실패 시 기존 데이터 보존

작성일: 2026-11-19. 기준: CSV 개선 PR #100 병합 후 원격 `develop`의 `957d47f`.
독립 작업 위치: `.recompute-atomic`, 브랜치: `fix/atomic-session-recompute`.

## 확인한 실제 문제

`POST /sessions/{session_id}/recompute`는 원본 탐지를 다른 캘리브레이션·알고리즘 조건으로 재처리하는 API다. 기존 구현은 대상 결과와 추적 상태를 삭제하고 대시보드 스트림을 초기화한 뒤 먼저 커밋했다. 이후 프레임 묶음마다 다시 커밋했다. 중간 오류로 요청이 실패해도 앞서 확정한 삭제나 부분 결과는 돌아오지 않았다.

예를 들어 기존 결과가 5묶음 있을 때 첫 번째·세 번째·다섯 번째 재계산에서 실패하면 각각 결과가 0·2·4묶음만 남는다. 사용자에게 실패를 반환하면서 기존 정상 결과도 잃는 것이 핵심 문제다. CSV 메모리 개선과 별개의 데이터 정합성 결함이며, 장애가 없을 때 정상 재계산만 검사하던 테스트로는 찾기 어려웠다.

운영에서 실제 결과 유실이 발생했다고 주장하는 사례는 아니다. 현재 코드에 실패를 주입해 기존 동작을 재현하고 수정했다. 원본 입력과 결과가 저장된 실서비스 기능의 트랜잭션 경계에 관한 문제다.

## 수정

- 일반 `/detections`는 기존처럼 묶음별로 커밋한다.
- 재계산 경로는 각 묶음을 저장·flush만 하고 마지막에 한 번 커밋한다.
- 대상 결과 삭제, 추적·PPE 상태 재구축, 대시보드 초기화·발행, 경고 갱신을 같은 트랜잭션에 포함한다.
- 중간 처리, DB 무결성 오류, 최종 커밋 오류에서 명시적으로 롤백한다. DB 무결성 충돌은 409로 반환한다.
- 아직 확정되지 않은 재계산 묶음의 성공 로그는 남기지 않는다. 전체 커밋 후 `recompute_complete`를 기록한다.
- 재계산 응답에는 처리한 묶음 수만 필요하므로 전체 처리 결과 목록을 보관하지 않는다.

DB 스키마·마이그레이션·운영 환경변수·위험 판정 기준은 바꾸지 않았다.

## 전후 검증 결과

별도 임시 SQLite DB를 만들고 원본 5묶음과 정상 대상 결과 5묶음을 준비했다. 사람 위치, 칼만 추적, PPE 상태, 위험구역 경고를 만들고 경고 확인(ack)도 저장했다. 실패 직전 대상 묶음의 대시보드 발행까지 실행해 DB 변경이 발생하도록 한 후 오류를 주입했다.

오류 종류는 HTTP 503, 실제 DB unique 제약 위반, 예상하지 못한 예외의 3가지이며 위치는 1·3·5번째 묶음이다. 총 9조건을 기준 코드와 수정 코드에 각각 실행했다. `session_id`를 가진 모든 테이블의 전체 열을 비교하고, 대상 CSV의 SHA-256도 비교했다. 일부 상태 테이블은 이 장면에서 비어 있으므로 모든 알고리즘 상태 조합까지 검증했다는 뜻은 아니다.

| 항목 | 기존 | 개선 후 |
| --- | ---: | ---: |
| 실패 후 기존 세션 데이터 전체 보존 | 0/9 | **9/9** |
| 첫 묶음 실패 후 대상 결과 | 0/5묶음 | **5/5묶음** |
| 중간 묶음 실패 후 대상 결과 | 2/5묶음 | **5/5묶음** |
| 마지막 묶음 실패 후 대상 결과 | 4/5묶음 | **5/5묶음** |
| 정상 5묶음 재계산의 커밋 수 | 6회 | **1회** |

수정 후 실패 9조건 모두 기존 CSV 해시도 유지했다. 이는 실패 후 데이터 보존을 위한 검증 조건의 결과이지 운영 장애율이나 데이터 유실 확률의 통계가 아니다. 커밋 횟수 감소를 처리 속도 향상률로 해석하지 않는다.

추가 회귀 검사에서는 마지막 커밋 자체가 실패하는 2조건에서도 기존 데이터가 보존됐고, 정상 완료 시 새 stream_id·seq=5·마지막 pair_id=5와 전체 결과 5묶음을 확인했다. 기존 단일 묶음 수신·중복 409·기능별 재계산·PPE 검증을 포함한 전체 백엔드 테스트와 엣지 테스트도 수행했다.

검증 결과: SQLite 백엔드 **147개**, 독립 로컬 PostgreSQL 백엔드 **147개**, 엣지 **61개** 통과. PostgreSQL은 기존 데모 DB를 건드리지 않고 별도 데이터 디렉터리·로컬 포트 55434·테스트 DB를 생성해 실행했다. 처음 실행은 Windows 샌드박스 restricted-token 오류로 실패했고, 동일 테스트 전용 서버를 권한 확장 실행해 검증했다. 종료 후 이 테스트 서버만 중지했다.

원본 실행 결과: `output/benchmarks/recompute-atomicity.json`. 재현 스크립트는 운영 DATABASE_URL을 사용하지 않고 독립 임시 SQLite DB를 강제로 생성한다. 기준 커밋의 기존 API를 불러와 같은 테스트 설정으로 비교한다.

```powershell
python tools/benchmarks/recompute_atomicity.py
python -m pytest --rootdir=. --confcutdir=. backend/tests -q
python -m pytest --rootdir=. --confcutdir=. ai/tests -q
```

## 범위와 절충

큰 재계산은 단일 트랜잭션의 시간·잠금·WAL 사용량이 커진다. 전체 입력도 여전히 메모리에 준비하므로 대규모 세션의 비동기 작업화·별도 결과 버전 생성은 후속 설계 대상이다. 실시간 입력과 같은 조건을 동시에 재계산할 때의 재시도·실행 제한 정책, 일정 시점의 원본 스냅샷 보장, 네트워크 단절로 커밋 성공 여부를 알 수 없는 경우의 멱등 응답까지 추가한 것은 아니다. 이번에 확인한 중간 실패 후 부분 결과 잔류를 해결하는 변경이다.

## 자소서 초안

안전관제 시스템의 백엔드에서 결과 재계산이 실패하면 기존 정상 데이터까지 유실될 수 있는 구조를 발견했습니다. 삭제와 프레임별 저장이 각각 커밋되는 것이 원인이었습니다. 처음·중간·마지막 처리 단계에 오류를 주입해 기존 결과가 일부만 남는 현상을 재현한 뒤, 삭제부터 재계산과 대시보드 갱신까지 하나의 트랜잭션으로 묶었습니다. HTTP 오류, DB 제약 위반, 예상하지 못한 예외를 조합한 9가지 조건에서 기존 데이터 전체 보존 결과를 0/9에서 9/9로 개선했고, CSV 해시와 경고 확인 상태까지 비교했습니다. 이를 통해 정상 동작뿐 아니라 실패 후 데이터 상태를 기준으로 정합성을 검증하는 역량을 길렀습니다.

금융권 지원에서는 재처리와 정합성 보장 경험으로, 공기업 지원에서는 누적 기록·증빙·처리 이력 보존 경험으로 연결할 수 있다. 실제 금융 거래를 처리했다거나 운영 장애를 복구했다고 바꾸어 쓰지 않는다. 면접에서는 “같은 9가지 재현 조건에서 기존 데이터 보존 여부를 확인한 결과”라고 수치의 범위를 설명한다.

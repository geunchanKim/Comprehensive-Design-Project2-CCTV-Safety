## 2. 시스템 구성

```
Tapo 카메라 2대 (RTSP, 1920×1080)
   ↓
노트북(엣지): 두 영상 시각 짝 맞추기 → YOLO11 사람·물체 탐지 + 포즈(발목) → 묶음 전송
   ↓  POST /detections
서버: 두 카메라 짝짓기 → 삼각측량 → 바닥 위치 → 추적 → 위험 경고
   ↓  POST /sessions/{id}/recompute  (같은 탐지로 다른 조건 다시 계산)
평가: 정답 위치와 1:1 비교
```

| 구성 | 담당 | 내용 |
| --- | --- | --- |
| 엣지 | 근찬 | 실시간 녹화·짝 맞추기(±50ms), 탐지(사람·의자·캐리어·가방), 발목 기반 발 위치 |
| 캘리브레이션 | 해민 | 기본(체커보드 내부 + 추정 외부), 정밀(ArUco 마커 PnP) |
| 서버 | 해민·근찬 | 짝짓기·삼각측량·추적·경고, 조건별 다시 계산 |
| 실험·평가 | 근찬 | pack 재전송, 1:1 채점, 기능별(ablation) 표 자동 생성, CI·자동 배포 |
| 시나리오·현장 | 성윤 | 진행표, 녹화 이름표, 기록지 |

### 실험 설계 (2×2 + 기능별)

|  | 기존 알고리즘 | 개선 알고리즘 |
| --- | --- | --- |
| **기본 캘리브레이션** | ① | ② |
| **정밀 캘리브레이션** | ③ | ④ |
- 촬영 때는 ①만 보내고, ②~④는 서버가 **같은 탐지 결과로 다시 계산**합니다. 탐지 결과가 같아서 조건 사이 차이는 알고리즘·캘리브레이션 차이만 반영합니다.
- 기능별 실험은 `algorithm=f-<기능 글자>`로 기능을 하나씩 켜서 계산합니다.

## 3. 개선 알고리즘

| 코드 | 기능 | 원리 | 노린 지표 | 개선에 포함 |
| --- | --- | --- | --- | --- |
| `g` | A 바닥 짝짓기 | 두 카메라 발 광선과 바닥 평면의 교점이 가까운 쌍끼리 헝가리안 매칭 (기존: 에피폴라 거리) | 오매칭 | ✅ |
| `c` | C 바닥 좌표 추적 | 바닥 (x, y) 칼만 예측 위치와 0.8m 안에서 사람 번호 연결 (기존: 카메라 트랙 번호 쌍) | ID 바뀜 | ✅ |
| `d` | D 한 카메라 보완 | 두 카메라 짝짓기 실패 시 한 카메라 광선과 발목 높이 평면 교점으로 기존 트랙만 갱신 | 놓침 | ✅ (`c` 필요) |
| `f` | F 경고 유지 | 1.0m 미만에서 켠 경고는 1.1m 이상에서 끔 (히스테리시스) | 경고 깜빡임 | ✅ |
| `a` | B 같은 쪽 발목 | 왼발끼리·오른발끼리 삼각측량 후 평균 | 발 위치 오차 | 실측에서 판단 |
| `e` | E 시간차 보정 | 두 사진 시각 차 × 추적 속도만큼 픽셀을 옮겨 다시 삼각측량 | 시간차 오차 | 실측에서 판단 |

**개선(`improved`) = `g + c + d + f`.** 설정값(칼만 잡음, 연결 거리 등)은 Unity 데이터 오프라인 시뮬로 정했습니다. 서버 결과가 시뮬과 소수점까지 일치하는 것도 확인했습니다.

## 6. 실측 평가 계획 (논의 안건)

### 방향

실측에는 Unity처럼 매 프레임 정답이 없습니다. 그래서 **사람이 정해진 좌표(격자점·정지선)에 서 있는 프레임만** 골라 정답으로 씁니다.

### 절차

| 단계 | 내용 | 담당 |
| --- | --- | --- |
| 1 | 녹화별로 사람이 격자점에 선 **프레임 구간**과 **좌표**를 표로 정리 (영상 + 기록지 + 플래시 시각) | 성윤·근찬 |
| 2 | 녹화를 서버로 전송 → 2×2 조건과 기능별 조건으로 다시 계산 | 근찬 |
| 3 | 1번 프레임에서만 채점: 위치 오차(평균·90%), 탐지율, 오매칭 | 근찬 |
| 4 | 조건별 비교표 + 통계 검정 | 근찬 |

**정답 표 양식 (안)**

| session_id | 시작 프레임 | 끝 프레임 | 사람 | 격자점 | x (m) | y (m) |
| --- | --- | --- | --- | --- | --- | --- |
| classroom-1014-s1-t1 | 120 | 165 | A | P3 | 2.0 | 3.0 |

### 지표별 근거 데이터

| 지표 | 실측 (정적 프레임) | Unity (전 프레임) |
| --- | --- | --- |
| 위치 오차 | ✅ 주 결과 | ✅ |
| 캘리브레이션 기본 vs 정밀 | ✅ 주 결과 | ❌ (정답 캘리브레이션이라 비교 불가) |
| 오매칭·탐지율 | ✅ | ✅ |
| ID 바뀜·경고 깜빡임·교차 구간 | ⚠️ 정답 궤적이 없어 어려움 | ✅ 주 결과 |
| B(발목)·E(시간차) 판단 | ✅ 정적 프레임 오차로 판단 | 참고 |

### 대학원생께 여쭙고 싶은 점

1. **정적 프레임만으로 평가해도 논문 근거로 충분한지.** 움직이는 구간 성능(ID 바뀜, 경고)은 Unity 결과로 보완하는 구성이 괜찮은지
2. **표본 수.** 격자점·회차가 몇 개면 조건 비교가 의미 있는지. 같은 프레임 쌍 비교라 대응 검정(Wilcoxon 등)을 쓰려고 하는데 적절한지
3. **동적 지표를 실측에서 볼 방법.** 예를 들어 정지선 도착 시각, 두 사람 사이 거리를 줄자로 잰 구간 등
4. **기능별 결과 서술.** 기능마다 노린 지표가 좋아졌다는 식(A: 오매칭, C: ID 바뀜, D: 놓침, F: 깜빡임)으로 써도 되는지
5. **F 채점 여유 구간(0.9~1.1m)** 과 **D의 오차·놓침 맞교환**을 보고하는 방식

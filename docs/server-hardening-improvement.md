# 설정 검증·위험 상태 조회·최신 상태 발행 개선

작성일: 2026-11-19. 전후 비교 기준 코드: `957d47f`(CSV 개선 #100 병합).
수정은 재계산 개선 #101 위에서 작업했으며, 기존 다른 worktree·미커밋 작업은 보존했다.

## 확인한 네 가지 문제와 수정

1. **잘못된 캘리브레이션 저장**: fx 또는 fy가 0인 행렬도 200으로 저장되어, 같은 합성 장면의 위치가 1개에서 0개로 사라졌다. 직접 등록·PnP 요청에서 행렬 형태·양수 초점거리·유한값을 검사하고 422로 거절한다. 오류 응답에 NaN/Infinity가 포함돼 JSON 직렬화가 실패하지 않도록 검증 오류 인코딩도 보완했다. 정상적인 검증 오류 구조는 유지한다.
2. **위험 경고 유지의 DB 조회 반복**: 사람이 20명이면 위험 상태 SELECT가 묶음마다 190회 발생했다. 현재 사람들의 상태를 조건별로 일괄 조회하고 요청 내에서 재사용한다. 400명씩 나누어 SQL 바인드 수를 제한한다. 400명 초과에서는 복수 배치 조회가 발생하므로 항상 1회라고 주장하지 않는다.
3. **과거 입력이 최신 경고 종료**: 촬영 시각 2000ms 입력 뒤 1000ms 입력이 도착하면 최신 snapshot이 과거 위치로 바뀌고 위험구역 경고가 종료됐다. 과거 입력의 원본 저장은 유지하면서 snapshot·seq·경고·카메라 관측 시각 갱신을 건너뛴다. 구역 편집으로 snapshot이 비어도 마지막 관측 시각으로 보호하며, 같은 촬영 시각의 별도 프레임은 허용한다. 재계산 스트림 초기화는 이 시각 기준을 초기화한다.
4. **SSE의 변하지 않은 전체 JSON 반복 조회**: 구독마다 0.25초마다 전체 대시보드 ORM 행을 가져왔다. 마지막 stream_id/seq와 다를 때만 snapshot 열을 반환하도록 SQL 조건을 추가했다. DB polling 횟수와 첫 구독·재접속·새 스트림 발행 규칙은 유지한다.

## 실제 전후 측정

`tools/benchmarks/server_hardening.py`는 기준 커밋의 backend를 임시 폴더로 추출하고 기준·수정 코드를 각각 별도 프로세스/SQLite DB에서 실행한다. 운영 DATABASE_URL은 사용하지 않는다. 원본 결과는 `output/benchmarks/server-hardening.json`이다.

| 항목 | 기존 | 개선 후 |
| --- | ---: | ---: |
| fx/fy=0 설정 변경 응답 | 200 | 422 |
| 잘못된 설정 변경 후 정상 카메라 설정 보존 | 0/2조건 | 2/2조건 |
| 해당 장면 위치 결과 | 1 → 0개 | 1 → 1개 |
| 사람 5명 위험 상태 SELECT/묶음 | 10회 | 1회 |
| 사람 10명 위험 상태 SELECT/묶음 | 45회 | 1회 |
| 사람 20명 위험 상태 SELECT/묶음 | 190회 | 1회 |
| 과거 입력 후 최신 촬영 시각 | 2000 → 1000ms | 2000ms 유지 |
| 과거 입력 후 위험구역 경고 | 활성 → 종료 | 활성 유지 |
| SSE 1.1초 관찰의 DB poll | 5회 | 5회 |
| 같은 관찰의 전체 snapshot 반환 | 5회 | 1회 |

위험 상태 조회는 20명 조건에서 99.47% 감소했다. 5/10/20명 각각 처음·반복 묶음의 총 6조건에서 위치·위험 응답의 SHA-256이 전후 동일했다. 위험 계산 자체의 사람 쌍 수를 줄인 것은 아니다. 원본에 보관한 risk_ms는 로컬 단일 표본이므로 일반적인 처리 시간 개선율로 주장하지 않는다.

SSE의 전체 JSON 반환이 줄었다는 결과를 SQL 횟수 80% 감소라고 바꾸어 쓰지 않는다. 서버 DB·프로세스 전체 부하나 다중 사용자 처리량은 별도 측정 대상이다. 이 검증은 합성 장면이며 운영에서 실제로 경고가 잘못 해제됐다는 보고가 아니다.

## 회귀 검증과 영향 범위

- 카메라 검증 실패 후 기존 K와 정상 탐지 결과 보존, PnP 입력 거절, NaN/Infinity 오류의 422 반환.
- 과거 입력의 저장, 최신 지도·경고·ack·카메라 관측 유지, 구역 수정 후 과거 snapshot 재발행 방지, 이후 새 입력 재발행.
- 위험 상태의 프로필 격리, 402명 ID의 쿼리 배치 경계, 경고 해제 거리 규칙.
- SSE의 idle·재접속·스트림 ID 변경 시 같은 seq 재발행.
- 기존 재계산 복원, 단일 탐지 수신·중복 거절, 기하·추적·보호구 및 엣지 테스트.

로컬 검증: SQLite 백엔드 **158개**, 엣지 **61개** 통과. PostgreSQL·프론트 검사 결과는 PR의 CI 상태로 확인한다.

API의 정상 응답 및 SSE 형식, 운영 환경변수·합의 거리/높이, 위험 분석 활성화 설정, DB 스키마는 변경하지 않았다. 잘못된 캘리브레이션을 기존보다 엄격하게 거절하며, 과거 입력의 최신 화면 발행은 의도적으로 달라진다. 따라서 모든 코드에 영향이 없다고 표현하지 않고, 이 두 동작 변경과 회귀 검사 범위를 함께 설명한다.

과거 입력에 대한 기하·추적·PPE 계산 전체를 새로 설계한 것은 아니다. 시계 초기화는 새 세션/명시적 재계산으로 다룬다. 인증·장치 소유권·동시 재계산 정책, Redis/메시지 브로커 도입, 구독자 간 polling 공유는 이번 범위가 아니다.

```powershell
python tools/benchmarks/server_hardening.py
python -m pytest --rootdir=. --confcutdir=. backend/tests -q
python -m pytest --rootdir=. --confcutdir=. ai/tests -q
```

## 실행력을 설명할 자소서 소재

“성공 응답만으로 정상이라고 판단하지 않고, 잘못된 설정·역순 입력·인원 증가·변화 없는 구독 조건을 직접 구성해 결과와 SQL을 확인했다. 발견한 문제를 검증·조회·발행 경계에서 고치고, 기존 결과 보존과 경고 동작을 함께 검증했다”는 과정이 핵심이다.

정량 성과로는 “사람 20명 조건의 위험 상태 조회 190회 → 1회, 비교한 6조건의 위치·위험 결과 해시 동일”을 사용할 수 있다. 신뢰성 사례로는 “지연 입력이 최신 경고를 해제하는 현상을 재현하고 최신 상태를 보존하도록 개선”을 사용할 수 있다. 운영 장애율·안전사고 감소나 금융 거래 처리 경험으로 바꾸어 쓰지 않는다.
